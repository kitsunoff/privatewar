# 11 — Navmesh generation on maps without a `.nav`

Research for `design/03-mapdata.md` decision 8 ("Maps without navmesh: warn, offer generation, never auto-generate"). Target: a player-hosted **listen server** (New Game menu, Steam P2P). Bots are `player.CreateNextBot` with our own A* over the navmesh. The dynamic-spawn fallback samples navmesh areas.

Evidence labels:

- `[wiki]`: wiki.facepunch.com page, fetched 2026-11-06 with `?format=text`;
- `[src]`: source file and line;
- `[forum/issue]`: URL;
- `[inference]`: my reasoning from the evidence;
- `[unverified]`: plausible, no source found; must be checked in game.

Source versions used:

- `ValveSoftware/source-sdk-2013` at `e1f1fd4` (`src/game/server/nav_*.cpp`, `gameinterface.cpp`). The GMod engine and its `navmesh` Lua bindings are closed source. Rubat (GMod maintainer) states that GMod "runs on the 2013 branch" and that "nothing about navmesh generation is changed in GMod" ([issue 4477](https://github.com/Facepunch/garrysmod-issues/issues/4477), [issue 2165](https://github.com/Facepunch/garrysmod-issues/issues/2165)). So SDK code is the best available model of GMod behaviour, but every claim taken from it is about the SDK, not proven for GMod;
- Valve Developer Community pages "Nav Mesh Editing", "Nav mesh", "Nav Mesh/Console commands" (read in a browser on 2026-11-06; the site blocks scripted fetches).

## TL;DR

| # | Question | Verdict |
| --- | --- | --- |
| 1 | Requirements | `navmesh.BeginGeneration()` from server Lua does **not** need `sv_cheats` (the cheat flag sits on the console command, not on the engine function). It needs at least one **walkable seed**: by default only the first `info_player_start`. Many PvP maps have none, so we must call `navmesh.AddWalkableSeed` for every spawn entity. Without seeds it fails silently: `IsGenerating()` is `false` right after the call. Console `nav_generate` needs `sv_cheats 1`. Nothing depends on P2P vs LAN. |
| 2 | On completion | The mesh is saved automatically to `garrysmod/maps/<map>.nav` (game folder, not `data/`), then the engine runs **`changelevel` to the same map**. Server and client Lua states reset; clients stay connected and reload. There is no Lua hook for "generation done". Detect the result on the next map load with a marker file in `data/` plus `navmesh.GetNavAreaCount() > 0`. |
| 3 | Blocking | Time-sliced: about 30 ms of work per server frame, so the game runs but at low FPS and with long single-frame hitches (area creation, saving). Duration: "a few minutes to a few hours, mostly about 5 minutes" (VDC); `ctf_2fort` about 110 s in GMod. Crashes on huge maps with displacements were reported and blamed on running out of memory; x86-64 reduces this. `nav_generate_incremental` only covers a radius around seeds. |
| 4 | Quality and speed | Missing areas come from missing seeds (stairs, separated areas). The slow part is "Computing mesh visibility", which `nav_quicksave 1` does **not** skip. Only `nav_max_view_distance 1` cuts it (and should shrink the `.nav` file a lot [unverified]), and that ConVar is cheat-protected. `nav_quicksave` is already `1` by default in GMod. |
| 5 | Client side | The whole `navmesh` / `CNavArea` API is server-only. Clients never receive the mesh. `GetAllNavAreas` builds a new Lua table of N userdata on every call: cache it once. |
| 6 | Common practice | Public bot addons refuse to run without a navmesh and show a message; gamemodes that offer generation add walkable seeds explicitly and rely on the automatic map reload. |

## 1. Requirements: `navmesh.BeginGeneration()` vs `nav_generate`

### 1.1 What each entry point checks

- The wiki documents only "Starts the generation of a new navmesh. This process is highly resource intensive and it's not wise to use during normal gameplay", realm Server. It lists no `sv_cheats` requirement [wiki `navmesh.BeginGeneration`].
- The console command is a thin wrapper with two checks. The engine function has neither [src `nav_mesh.cpp:2600-2609`]:

  ```cpp
  void CommandNavGenerate( void )
  {
      if ( !UTIL_IsCommandIssuedByServerAdmin() )
          return;
      TheNavMesh->BeginGeneration();
  }
  static ConCommand nav_generate( "nav_generate", CommandNavGenerate, "...", FCVAR_GAMEDLL | FCVAR_CHEAT );
  ```

- So `nav_generate` from the console needs `sv_cheats 1` and the listen-server host [src above; VDC "Nav Mesh Editing": "generated by using the nav_generate command ... which requires sv_cheats 1"]. The VDC "Nav mesh" page also says `nav_edit 1` is needed. In the SDK only `nav_analyze` checks `nav_edit` [src `nav_mesh.cpp:2637-2645`].
- `navmesh.BeginGeneration()` presumably calls `TheNavMesh->BeginGeneration()` directly, so neither check applies [inference]. Checked in game: see "To verify in game", item 1.

### 1.2 What `BeginGeneration` does first (SDK)

From `CNavMesh::BeginGeneration` [src `nav_generate.cpp:3416-3486`]:

1. It fires the game event `nav_generate`.
2. Outside L4D (`#else` branch) it runs `engine->ServerCommand( "bot_kick\n" )` [src `:3437`]. Whether GMod's `bot_kick` exists and removes `player.CreateNextBot` bots is `[unverified]`. Our design should kick its own bots first anyway.
3. It runs `DestroyNavigationMesh()`. From this moment `GetAllNavAreas()` is empty, so bots and the spawn sampler lose the mesh at once [src `:3453`].
4. It builds ladders and calls `AddWalkableSeeds()`. The default implementation seeds **only the first entity** of class `GetPlayerSpawnName()` [src `:3394-3410`]. The default name is `"info_player_start"` [src `:4078-4085`; wiki `navmesh.GetPlayerSpawnName`].
5. If there are no seeds, it prints `"No valid walkable seed positions.  Cannot generate Navigation Mesh."` and returns with `m_generationMode = GENERATE_NONE` [src `:3472-3477`]. From Lua this shows only as `navmesh.IsGenerating() == false` immediately after the call [inference].

### 1.3 Walkable seeds from Lua

- `navmesh.AddWalkableSeed(pos, normal)`: "Add this position and normal to the list of walkable positions, used before map generation" [wiki]. `navmesh.ClearWalkableSeeds()` clears them [wiki]. `navmesh.SetPlayerSpawnName(class)` changes which class is auto-seeded [wiki].
- Lua seeds survive into generation. `DestroyNavigationMesh` does not clear them; they are cleared only at the end [src `nav_generate.cpp:4006`].
- Bug "all remaining seeds ignored after a redundant seed" was fixed on dev in 2017 [forum/issue [3221](https://github.com/Facepunch/garrysmod-issues/issues/3221)].
- On a dedicated server, `AddWalkableSeed` spams `UTIL_GetListenServerHost() called from a dedicated server` every frame [forum/issue [2403](https://github.com/Facepunch/garrysmod-issues/issues/2403)]. This does not apply to our listen-server target.

### 1.4 Listen server from the New Game menu, P2P

- Nothing in the generation path depends on the network mode. The output path comes from the game directory (§2.1) [src `nav_file.cpp:992-1003`]. Generation runs on the host machine, which is the server [inference].
- The final `changelevel` (§2.2) is the only P2P-sensitive step. `notes/10-changelevel-and-phase-sync.md` §1 records a 2026 report that nobody can join a P2P server after `changelevel` [forum/issue, see note 10].

## 2. What happens when generation finishes

### 2.1 Saving: automatic, to `garrysmod/maps/`

- The final state `SAVE_NAV_MESH` [src `nav_generate.cpp:3993-4044`]:

  ```cpp
  m_generationMode = GENERATE_NONE;
  m_isLoaded = true;
  ClearWalkableSeeds();
  HideAnalysisProgress();
  if (Save()) Msg( "Navigation map '%s' saved.\n", GetFilename() );
  ...
  if ( m_bQuitWhenFinished )      engine->ServerCommand( "quit\n" );
  else if ( restart )             engine->ChangeLevel( STRING( gpGlobals->mapname ), NULL );
  ```

- File name: `"<gamedir>\maps\<map>.nav"` [src `nav_file.cpp:188-189`, `:992-1003`]. It is written with `filesystem->WriteFile( filename, "MOD", ... )` [src `:1204`]. In GMod the game dir is `garrysmod/`, so the file is `garrysmod/maps/<map>.nav`, **not** `data/` [inference; VDC: "`<game>/maps/<mapname>.nav`"]. Lua cannot write there, so we cannot move or copy the file ourselves [inference].
- If writing fails, a backup is written as `<file>.failedsave` [src `:1204-1218`].
- Loading reads `maps/<map>.nav` from the `MOD` path first, then from the BSP [src `nav_file.cpp:1401-1409`]. If the BSP size changed (for example a workshop map update), the mesh still loads, with only a developer warning (`m_isOutOfDate = true`) [src `:1495-1507`].
- Workshop-packed `.nav` files had loading problems in 2014–2016 [forum/issue [1455](https://github.com/Facepunch/garrysmod-issues/issues/1455), [2480](https://github.com/Facepunch/garrysmod-issues/issues/2480)]. Whether Workshop-packed `.nav` files load correctly today is [unverified].

### 2.2 The map reloads

- With `restart = m_generationMode != GENERATE_INCREMENTAL`, a full generation always ends with `engine->ChangeLevel(<same map>)` [src `nav_generate.cpp:4008`, `:4026-4029`]. VDC confirms this for analysis: "use nav_analyze ... It will reload the map upon completion".
- Newer Valve games have `nav_restart_after_analysis` ("If set to 1, ... restart the server. Turning this off can cause crashes") [VDC "Nav Mesh/Console commands"]. It is not in SDK 2013, and whether it exists in GMod is `[unverified]`.
- Consequences (from note 10): `ShutDown` runs, then both Lua states are rebuilt. Human clients stay connected and reload the map. Our phase machine restarts at `LOBBY`. Bots lose their Lua state.
- Issue 2332's code polled `IsGenerating()` and ran `changelevel` itself, but "it never reached the changelevel command"; Rubat could not reproduce the crash in that report [forum/issue [2332](https://github.com/Facepunch/garrysmod-issues/issues/2332)].
- Incremental generation (`nav_generate_incremental`) does **not** restart [src `nav_generate.cpp:4008`].

### 2.3 Detecting completion from Lua

- `navmesh.IsGenerating()`: "Whether we're currently generating a new navmesh" [wiki]. It turns `false` in `SAVE_NAV_MESH` just before `Save()` and `ChangeLevel` [src above]. Polling it can catch at most one or two frames before the reload [inference].
- There is no GMod hook for generation progress or completion. The wiki page list has no `nav_generate` game event page and no `GM:` hook with "nav" in its name [wiki page list]. The engine fires the game event `nav_generate` only at the **start** [src `nav_generate.cpp:3418-3422`]. Whether `gameevent.Listen("nav_generate")` receives it is `[unverified]`.
- No progress percentage reaches Lua. The engine sends `PANEL_NAV_PROGRESS` viewport-panel messages to all clients [src `nav_generate.cpp:3593-3620`]. That is a CS/TF2 client panel; whether GMod clients show anything is `[unverified]`. Console lines such as `"Generation complete!  %0.1f seconds elapsed."` are not readable from Lua [inference].
- Reliable detection is cross-map [inference]:
  - before `BeginGeneration`, write `data/<gm>/navgen.json` = `{ map, startedAt, seeds, cheatsChanged }`;
  - on the next load of that map, if the marker exists: `GetNavAreaCount() > 0` means success, otherwise failure (crash, kill, or a failed save); delete the marker.
- When the navmesh is loaded: the server loads it in `ServerActivate` **after** `LevelInitPostEntityAllSystems` [src `gameinterface.cpp:1128-1142`]. So it may not be loaded yet when Lua's `InitPostEntity` runs [inference]. Check `navmesh.GetNavAreaCount() > 0` in the first `Think` or later (or poll it on a timer), not in `Initialize`.
- `navmesh.IsLoaded()`: "Returns true if a navmesh has been loaded when loading the map" [wiki]. Generation also sets it to `true` [src `nav_generate.cpp:4005`]. `GetNavAreaCount() > 0` is the more direct test [inference].

## 3. Blocking, duration, crashes

### 3.1 Time-sliced, but heavy

- `CNavMesh::Update` runs "on each game frame" and calls `UpdateGeneration( 0.03 )` while generating [src `nav_mesh.cpp:252-262`]. It is driven from `CServerGameDLL::GameFrame` [src `gameinterface.cpp:1238`]. Each state loop checks `Plat_FloatTime() - startTime > maxTime` and yields [src `nav_generate.cpp:3655-3660` and the other states].
- So the server does not freeze outright: Lua timers and HUD keep running. Every server frame gets about 30 ms of extra work, and on a listen server that frame is the host's frame [inference].
- Some steps are a single unsliced call and cause long hitches [src]:
  - `CREATE_AREAS_FROM_SAMPLES` → `CreateNavAreasFromNodes()` in one frame [src `nav_generate.cpp:3668-3690`];
  - `EndVisibilityComputations()` [src `:3785`];
  - `Save()` at the end.
- User reports: "the game hung up for a very long time ... freezing off and on" during generation [forum/issue [4477](https://github.com/Facepunch/garrysmod-issues/issues/4477)]. Rubat: "The fact that it appears to be stuck at that point doesn't mean it actually is" [forum/issue [2165](https://github.com/Facepunch/garrysmod-issues/issues/2165)].
- Analysis phases in order: hiding spots → encounter spots → sniper spots → mesh visibility → earliest occupy times → (light intensity) → custom → save [src `nav_generate.cpp:3703-3990`].
- The light-intensity step needs `NAV_ANALYZE_LIGHT_INTENSITY` and a listen-server host. It **teleports the host player** to each area (`host->SetAbsOrigin( eyePos )`) [src `:3846-3920`]. GMod exposes `CNavArea:GetLightIntensity` [wiki], so this step may run in GMod [unverified].

### 3.2 Durations reported

| Source | Map | Time |
| --- | --- | --- |
| VDC "Nav Mesh Editing" | general | "a few minutes to a few hours, but mostly about 5 minutes. Large forests ... may take a long time" |
| [issue 3893](https://github.com/Facepunch/garrysmod-issues/issues/3893) | `ctf_2fort` | about 110 s in GMod vs 50 s in TF2 (reporter); Rubat measured them as equal with `nav_quicksave 0` |
| [issue 2165](https://github.com/Facepunch/garrysmod-issues/issues/2165) | large map | "for the last nine hours ... stuck at 'finding hiding spots 2%'" |
| [issue 5375](https://github.com/Facepunch/garrysmod-issues/issues/5375) | `gm_harborside`, `gm_dark forest` | Rubat: they pass sampling "and move onto a very slow `Computing mesh visibility..` stage" |

### 3.3 Crashes

- [5375](https://github.com/Facepunch/garrysmod-issues/issues/5375): crashes during "Sampling walkable space" on huge maps. A reporter saw it "only ... on maps with displacements". Rubat could not reproduce it and assumed the process ran out of memory.
- [5476](https://github.com/Facepunch/garrysmod-issues/issues/5476) (2023, 32-bit): crashes "when saving the navmesh. It could be an out of memory issue. Try the `x86-64` beta."
- [5845](https://github.com/Facepunch/garrysmod-issues/issues/5845) (2024): x86-64-generated `.nav` files crashed on load. Fixed; such files "will need to be deleted and re-generated". A host with an old bad file must delete it by hand [inference].
- [3999](https://github.com/Facepunch/garrysmod-issues/issues/3999) (2019): crash during generation, fixed on dev.
- [2332](https://github.com/Facepunch/garrysmod-issues/issues/2332) (2015): crash after save with `BeginGeneration`; could not be reproduced.

### 3.4 Incremental and "quick" modes

- `nav_generate_incremental`: "Run the generation process from walkable markers instead of on the entire mesh" [VDC], limited by `nav_generate_incremental_range` (default 2000) [src `nav_generate.cpp:43`]. It forces `nav_quicksave 1`, keeps existing areas and **does not reload the map** [src `:3441-3445`, `:4008`]. There is no Lua entry point: `BeginGeneration` takes no argument [wiki]. It would need `RunConsoleCommand` plus `sv_cheats` [inference].
- No "quick" mode skips visibility, see §4.3.

## 4. Quality issues and fixes

### 4.1 Missing areas

- Sampling flood-fills from seeds: "Starting at a player spawn point, walkable space is sampled by 'flood-filling' outwards" [VDC]. "Maps that have very steep stairs, ramps, or hills may confuse the generation system, resulting in the Navigation Mesh not covering the entire map. To solve this, ... place additional walkable markers" [VDC "Nav Mesh Editing"].
- Areas not reachable from any seed (team-separated spawn rooms, areas behind closed doors or breakables) get no mesh [inference from the flood-fill]. Possible fixes [inference]:
  - a seed at **every** spawn entity (all spawn classes), traced down to the ground; optionally also at doors, ladder dismount points and teleport exits;
  - opening and removing all `func_door*` and `prop_door*`, and removing `prop_physics*`, `func_breakable` and `func_physbox` before generating. This is safe because the map reloads afterwards.
- `nav_generate_fencetops 0` should keep areas off fence tops, which otherwise make bots path over fences [inference].

### 4.2 `nav_quicksave`

- SDK description: "Set to one to skip the time consuming phases of the analysis". The SDK default is `"1"` [src `nav_mesh.cpp:48`]. In GMod "now nav_quicksave is defaulted to 1" [forum/issue [2165](https://github.com/Facepunch/garrysmod-issues/issues/2165)].
- What it actually skips: Rubat says "nav_quicksave only skips 2 things: ComputeSpotEncounters and ComputeSniperSpots" [forum/issue [4477](https://github.com/Facepunch/garrysmod-issues/issues/4477)]. This matches the SDK [src `nav_area.cpp:3958`, `:4104`] (plus the CS-only occupy times [src `nav_file.cpp:868`]). Hiding spots and **mesh visibility still run**.
- So `nav_quicksave 1` saves little, and it is already the default. "Computing mesh visibility ... was first introduced in Left 4 Dead and was added to the 2013 SDK base", so the old trick from SDK 2007 no longer helps [forum/issue 4477].

### 4.3 `nav_max_view_distance`: the real speed and size lever

- `ConVar nav_max_view_distance( "6000", FCVAR_CHEAT, "Maximum range for precomputed nav mesh visibility (0 = default 1500 units)" )` [src `nav_area.cpp:63`]. It bounds `ComputeVisibilityToMesh` [src `:5580-5590`]. The GMod default is `[unverified]`.
- With a visibility range of 1 unit, `ComputeVisibilityToMesh` finds almost nothing, so this phase becomes cheap and the `.nav` file much smaller [inference; size to be measured in game]. The issue-3221 reporter used `nav_max_view_distance 1` to "disable" visibility [forum/issue [3221](https://github.com/Facepunch/garrysmod-issues/issues/3221)].
- Cost of setting it to 1: the precomputed area-to-area visibility (`CNavArea:IsPotentiallyVisible`, `GetVisibleAreas` [wiki]) becomes nearly empty. Our design uses traces for line of sight (`design/03-mapdata.md` decision 7), so nothing is lost [inference].
- Catch: it is `FCVAR_CHEAT`. `ConVar:SetFloat` "can only be ran on ConVars created from within Lua" [wiki `ConVar:SetFloat`]. So the "fast" path needs `sv_cheats 1` for the duration [inference]. In Source, setting `sv_cheats` back to 0 reverts all cheat ConVars to their defaults [inference, unverified for GMod]. That is harmless here, because the value is needed only until the map reloads.
- Side effect of `sv_cheats 1` on a P2P server: every connected client can run cheat commands (for example `ent_create`, `god`) until the map reloads [inference]. Only offer it in the lobby, and preferably only when the host is alone or accepts the risk.

### 4.4 `nav_analyze`

- `nav_analyze` "just reruns nav_generate by skipping 2 steps: SAMPLE_WALKABLE_SPACE and CREATE_AREAS_FROM_SAMPLES" [forum/issue 4477]. It requires `nav_edit 1` [src `nav_mesh.cpp:2641`] and reloads the map [VDC].
- A full `nav_generate` already includes the analysis (VDC: "does a nav_analyze in the end"), so running `nav_analyze` afterwards repeats work. We do not need a separate analyze [inference].

## 5. Client side and API cost

- Every `navmesh.*` and `CNavArea:*` page lists realm **Server** (`navmesh.GetAllNavAreas`, `GetNavArea`, `GetNearestNavArea`, `Find`, `GetNavAreaCount`, `IsLoaded`, `IsGenerating`, `CNavArea:GetRandomPoint`, ...) [wiki]. The navmesh lives only in the server game DLL (`TheNavMesh`, `src/game/server/`) [src]. Clients cannot query it, and P2P clients do not need the `.nav` file [inference].
- Client-side needs (minimap, debug draw) need data sent over net from the server [inference].
- `navmesh.GetAllNavAreas()` returns a fresh "integer indexed table of all CNavAreas" [wiki], so each call allocates N userdata [inference]. Mesh size scales with the map [inference].
- Recommendation: build our caches (area list, spawn sample of about 200 points, area→index map) once after the mesh is loaded. Never call `GetAllNavAreas` per think [inference].
- `GetNavAreaCount` warns that IDs are "not always sequential" [wiki], so do not iterate `GetNavAreaByID(1..count)`.
- `navmesh.GetNavArea(pos, beneathLimit)` "will properly see blocked CNavAreas" and `GetNearestNavArea` ignores blocked areas [wiki]. Both are point queries backed by the engine's spatial grid, so a few calls per bot think should be cheap [inference].
- `navmesh.Load()` "Calling this function too soon, causes the Server to crash" [wiki]. The cause was a missing GameRules check; Rubat said it would be fixed on dev [forum/issue [5632](https://github.com/Facepunch/garrysmod-issues/issues/5632)]. We do not need `Load`, because the reload after generation loads the file [inference].

## 6. Common practice in public addons

Public bot addons refuse to run without a navmesh and show a message; gamemodes that offer generation add walkable seeds explicitly and rely on the automatic map reload. None shows real progress, only elapsed time or a "be patient" message.

## Recommendations for `design/03-mapdata.md` decision 8

The design decision stands (warn, offer, never auto-generate). A concrete flow:

### Preconditions for showing the "Generate navmesh" button

1. The server state is `LOBBY` (not in a match). The map is the current map: generation works only on the loaded map, so "generate for another map" means changing level first [inference].
2. After the first `Think` past `InitPostEntity`, `navmesh.GetNavAreaCount() == 0` (§2.3).
3. `navmesh.IsGenerating() == false`.
4. The caller holds the host privilege (`00-core.md` decision 7). On P2P this is normally the listen host.
5. Optional: `file.Exists("maps/" .. game.GetMap() .. ".nav", "GAME")` is true but the mesh is not loaded. Then show "a .nav file exists but did not load (corrupt or from an old x86-64 build); delete `garrysmod/maps/<map>.nav` and regenerate" (§3.3, issue 5845) instead of a plain Generate button.

### What the host sees before starting

A confirmation dialog stating:

- "Takes from about 1 minute to over an hour on huge maps. The game will stutter heavily and may look frozen. Do not close it."
- "When done, the map reloads automatically. Everyone stays connected; the lobby resets."
- "Saved to `garrysmod/maps/<map>.nav`; needed only once per map on this computer. Other players do not need the file."
- "Large maps can crash the game (out of memory); the 64-bit branch is more stable."
- A checkbox "Fast mode (smaller file, much faster): temporarily enables sv_cheats", default **off**. It is shown only when other humans are connected; when the host is alone, fast mode is safe to default on. This is the only setting worth exposing (§4.3).

### What the server does on confirm

1. Write the marker `data/<gm>/navgen.json` = `{ map, startedAt = os.time(), fast, cheatsWasOn }`.
2. Kick our bots, and set a flag that stops bot creation and the spawn sampler.
3. Broadcast a lobby message to all clients: "Host is generating a navmesh; the map will reload."
4. Seeds: `navmesh.ClearWalkableSeeds()`. Then, for every entity of the spawn classes from decision 3 (`info_player_start`, `info_player_deathmatch`, `info_player_terrorist`, `info_player_counterterrorist`, `info_player_teamspawn`, `info_player_combine`, `info_player_rebel`, `gmod_player_start`, plus Lua map-file spawns), trace down up to 4096 u with `MASK_PLAYERSOLID_BRUSHONLY` and call `navmesh.AddWalkableSeed(tr.HitPos, tr.HitNormal)`. Add the host's position if the host is on the ground.
5. Optional map cleanup (§4.1): fire `Open` on doors and remove physics props and breakables. This is safe because the map reloads.
6. If fast mode: `RunConsoleCommand("sv_cheats", "1")`, `RunConsoleCommand("nav_max_view_distance", "1")`, `RunConsoleCommand("nav_generate_fencetops", "0")`. Wait one tick so the commands apply.
7. Call `navmesh.BeginGeneration()`. If `navmesh.IsGenerating()` is false on the same tick, it failed (no valid seeds): delete the marker, restore `sv_cheats`, and show "Could not find a walkable start point on this map".
8. While generating: the HUD shows "Generating navmesh… mm:ss elapsed" from a Lua timer (no percentage exists). Gameplay input stays disabled.

### What happens after

1. The engine saves the `.nav` and runs `changelevel` to the same map. Lua restarts and clients reload (note 10).
2. On the new load, in the first `Think` after `InitPostEntity`, read the marker:
   - `GetNavAreaCount() > 0`: success. If fast mode was used and `cheatsWasOn` is false, run `RunConsoleCommand("sv_cheats", "0")`. Show the host "Navmesh generated (N areas)". Build the caches once (§5). Delete the marker.
   - `GetNavAreaCount() == 0`: failure (crash, or the host quit). Show "Last navmesh generation on this map did not finish". Offer: try again, try fast mode, search the Workshop for "`<map>` navmesh", or pick another map. Delete the marker.
3. Bots and dynamic spawns become available in the lobby for this map.

### Things not to do

- Do not call `navmesh.Load()` or `navmesh.Save()` manually. Generation saves and reloads by itself; `Load` too early crashes (§5).
- Do not poll `IsGenerating()` to trigger our own `changelevel`; the engine already does it (§2.2).
- Do not offer `nav_generate_incremental` in MVP: it needs cheats, covers only a radius, and does not reload (§3.4).
- Do not run a separate `nav_analyze` after generation; it is included (§4.4).

## To verify in game

Use a clean GMod install (main branch and x86-64), New Game → P2P, a map without `.nav` (for example `de_dust2` from CS:S content, a small workshop DM map, and one large displacement map).

1. **No cheats needed:** with `sv_cheats 0`, run `lua_run navmesh.BeginGeneration() print(navmesh.IsGenerating())` on a map **with** `info_player_start`. Expected: `true`, and console output "Generating Navigation Mesh...".
2. **No-seed failure:** on `de_dust2` (expected to have no `info_player_start` [unverified]), run the same command. Expected: `false` and the console line "No valid walkable seed positions". Then add seeds from `info_player_terrorist` with `AddWalkableSeed` and retry. Expected: `true`.
3. **`bot_kick`:** add 2 bots with `player.CreateNextBot`, then start generation. Record whether the bots are kicked.
